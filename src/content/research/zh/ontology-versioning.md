## 结论先行

柏讯平台的本体 = 实体与关系的业务声明（业务名、绑定数据集、主键列、关系指向）。2026-11-01 起，本体具备完整的语义版本能力，全部能力已在真实客户环境演练通过（演练环境：5 个实体、5 条关系的存量本体）。

| 能力 | 说明 | 入口 |
| --- | --- | --- |
| 变更事件 | 每次创建/更新/删除落一条不可篡改事件，含变更前后全量 | 自动记录，无需操作 |
| 版本快照 | 「进一版」=打一份当前态快照，带内容指纹；日快照每日自动、零变更跳过 | 控制台实体页「打发布版」按钮 |
| 版本对比 | 任意两版逐条对比：新增/删除/字段级改动（含改动前后值） | 版本行「对比当前」按钮 |
| 版本导出 | 导出 JSON 或 YAML，可指定版本或当前态，可附变更出处 | 版本区「导出」按钮 |
| 回滚 | 回到任一版本：先出计划预览，确认后逐条执行，历史只增不减 | 版本行「回滚到此版」按钮（仅 owner） |
| 完整性自检 | 「事件折叠结果 vs 当前态」比对，暴露绕过写面的直改 | 版本区「完整性自检」徽章 |

真机演练八步全部通过：打发布版 → 修改一个实体 → 未发布变更计数为 1 → 字段级对比命中预期 → 导出 JSON 与 YAML → 回滚后当前态与目标版本指纹一致 → 再次打版如实提示「内容一致，未新增版本」→ 完整性自检一致。

## 此前的问题：只有「当前态」

版本机制上线前，本体只有一份当前态，三个动作全部无痕：

| 动作 | 版本机制上线前 | 上线后 |
| --- | --- | --- |
| 改主键列或注记 | 原地覆写，无任何留痕 | 事件记录改动前后全量，可在版本对比中看到字段级差异 |
| 删除实体或关系 | 删除即消失 | 事件保留被删对象的全量内容 |
| 拿走本体 | 无导出口 | JSON/YAML 一键导出，文档自带内容指纹供校验 |

「未发布变更」的口径是事件计数：最近一次快照之后落下的变更条数。两次修改同一条实体会计为 2 条未发布变更，而版本对比显示 1 条净改动——两个数字回答两个不同的问题，都以真实数据呈现。

## 设计：四条决策

**决策一：事件与本体同库同事务。** 事件写入失败 = 本体写入失败。跨库双写无法保证一致，而「本体变了但没有事件」正是这套机制要消灭的缺陷形态。写面收敛到唯一写入口：控制台操作、AI 声明动作、回滚执行三条路径全部经同一入口，各自带操作者与来源标记。

**决策二：内容指纹只覆盖语义内容。** 快照指纹（digest）是对规范化的本体内容做哈希：条目排序、键序、类型形态全部归一后计算，不含时间戳。同一内容在任何时刻计算出的指纹恒一致——回滚到某版本后再打版，系统会如实提示「与 vN 内容一致」而不新增版本，这就是指纹一致性的直接应用。

**决策三：快照是发布决策，不是变更日志。** 日快照每日一次、零变更静默跳过；手动发布版随时可打、可带版本标签；同一 digest 不重复落快照。日版是时间线，手动版是发布决策，两者语义不同、各自保留。

**决策四：回滚 = 按计划再写一遍。** 回滚不是把表覆盖回旧状态——那会制造一段没有事件的历史空洞。回滚先生成计划预览（将创建/更新/删除哪些条目），owner 确认后逐条执行，每条落一条回滚事件；执行中途任一步校验失败即如实停止，已执行部分留有事件、可再次回滚修正。因此回滚本身永远可被再次回滚。

## 应用场景：谁在用、怎么用

- **客户管理员**：在控制台实体页查看版本时间线与未发布变更数；重要节点（如「冒烟本体定稿」）打一个带标签的发布版；发现改坏时回滚到任一发布版。
- **AI 消费面**：柏讯供给面经公开检索读取本体导出物；`schema_version` 是导出格式版本号，消费方据此判断文档形状。
- **平台运维**：完整性自检是「绕过写面的直改」的唯一落地检测——事件折叠结果与当前态不一致时，自检红、差异条目逐条列出。

## 边界与恢复

两条边界如实声明：

1. **绕过写面的直改不进事件流。** 任何绕过唯一写入口的直改（如运维手工改库）不产生事件——这类改动由完整性自检暴露（当前态与事件折叠结果不一致即红），不由事件流解释。事故运维确需直改时，改完应立即补打一份手动发布版把状态收进版本历史。
2. **语义版本不能替代库级备份。** 版本机制只覆盖本体语义（实体与关系），不覆盖数据行与平台其它数据。语义版本回滚用于「这版和上版差了什么、回到某版」；库损坏或误删一切走每日库级备份恢复。两条恢复线互补、不互替。
