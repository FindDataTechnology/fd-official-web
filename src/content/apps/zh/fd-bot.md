fd-bot 是我们把 IM 接入从每个应用进程里搬出来之后的那一层。它持有平台凭据与连接，
做验签与解密，把各家原生载荷规范化成一份信封，把发送结果分类后返回。它不做房间、
席位、计费、话术——那些属于调用方。

一句话划边界：**fd-bot 知道「这个平台允许你做什么」，不知道「你要拿它做什么」。**

## 为什么要有这一层

协议代码原先住在应用镜像里。这带来三个可测量的代价：

- 改一句群文案、调一个超时，要走出片链（快照 → 构建 → 推送 → 声明 → 滚版）。
- 契约、实现、能力闸分处三地：新平台落地时漏声明不会红，只会在面板上写成「这条腿寄不回去」。
- 每个应用实例各自连平台，N 个实例就是 N 条长连接、N 份凭据、N 个断线重连状态机。

搬出来之后：加一个平台 = 一个模块 + 一次重启。

## 它拥有的一条语义

只有一条：**能力披露**。每个平台适配器必须声明自己的出流形态：

| `outbound.mode` | 含义 |
|---|---|
| `url-keyed` | 凭据在 URL / body / header 里，无调用方 IP 白名单——换出口不受影响 |
| `proactive-ip-gated` | 能主动发，但只从白名单 IP |
| `passive-window` | 只能在一个近期入站打开的窗口内回复 |
| `none` | 没有出流路径 |

这条声明与实现写在同一个文件里，服务启动时校验：**缺声明 = 进程起不来**，不是一个警告。
理由是实测过的——某条腿曾经漏声明，面板把它报成「寄不回去」，而它明明有发送接口。

## 七条腿

| 平台 | 入站 | 出流能力 |
|---|---|---|
| 企业微信智能机器人 | 长连接（主动外连，免公网回调） | `url-keyed`（实测） |
| 企业微信自建应用 | 回调 | `proactive-ip-gated` |
| 企业微信群机器人 | 无（只出不进） | `url-keyed` |
| 微信公众号 | 回调 | `proactive-ip-gated` |
| 飞书 / Lark | 长连接或回调 | `url-keyed` |
| Slack | 回调 | `url-keyed` |
| Telegram | 轮询或回调 | `url-keyed` |

企业微信那条腿值得单说：换成官方 SDK 的长连接之后，它不再受「企业可信 IP」约束，
也不再只有一小时的被动回复窗口。实测在**零入站**的情况下主动发送成功，
所以它的能力是如实的 `url-keyed`——这是第一条换出口也不会断的企微腿。

## 契约

```
POST   /v1/bindings          建一条腿；返回能力与回调地址
GET    /v1/bindings          列出，带连接健康
DELETE /v1/bindings/:id      停连接再退休（不硬删）
POST   /v1/send              发送；失败带分类，不带 5xx
POST   /v1/callbacks/:p/:s   平台回调（POST 与 GET 握手）
GET    /v1/media/:ticket     短期取件地址
```

事件信封固定，调用方不必按平台分支解析：

```json
{
  "platform": "wecom-bot",
  "bindingId": "b_...",
  "chatKey": "wr...",
  "chatType": "group",
  "senderId": "...",
  "senderName": "...",
  "text": "...",
  "media": [{ "kind": "image", "url": "/v1/media/..." }],
  "platformMessageId": "...",
  "receivedAt": 1795180975208
}
```

## 三件常被问的事

**发送失败为什么返回 200？** 因为「出口地址不被接受」和「被动回复窗口已关闭」是**平台的判定**，
不是服务的故障。用 5xx 会让通用重试层去重试一个永远不会成功的调用。所以它们以
`200 {ok:false, failure}` 返回，分类由我们自己判定——不做平台措辞的子串匹配，那套语法平台随时能改。

**媒体为什么给地址不给字节？** 字节直传会把传输层变成一个需要配额的存储服务。
信封里是 HMAC 签名的短期票据（默认 5 分钟），取件时才按需下载并解密。**不接受调用方提供的
任意 URL**——SSRF 面在服务内部关闭。

**服务挂了会怎样？** 调用方拿到可判定的失败信号（连接失败 / 超时 / 非 2xx），
自己决定排队还是告警。服务不会用空集或成功状态掩盖自己不可用——「传输层挂了」和
「没人在发消息」必须是两个可区分的状态。
