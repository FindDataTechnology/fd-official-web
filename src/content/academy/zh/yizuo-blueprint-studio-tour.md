## 学完你能做什么

把一句业务描述（比如「盘前汇总隔夜要闻与持仓异动，出晨会纪要」）落成一份**蓝图**，走完整条生产线：校验 → 批准 → 铸造 → 试跑 → 签字 → 再铸上架——得到一支**真的跑通过**、可以装进你工作区的智能体团队。你还会看懂试跑报告里每个徽章的含义：哪些断言是机器判的、哪条是评审模型判的、模型「没跑成」和「证据不足」差在哪里。

## 前置条件

- 一个壹座账号，登录后左侧导航能看到「蓝图构造间」。
- 平台的模型车道可用（判据腿要用一个便宜的评审模型；没配好车道时构造间会如实告诉你，不会假装通过）。
- 不需要会写代码。蓝图的结构段（岗位编制、验收断言）用表单加少量 JSON 就能完成；也可以把需求交给「蓝图构造师」用自然语言起草。

## 先认识这块界面

![蓝图构造间：左边是你的全部蓝图（状态徽章与版本号），右边是编辑区；顶部一排按钮就是整条生产线的动作](https://cms.finddatatech.cloud/uploads/blueprint_studio_01_studio_overview_485935e252.png)

左列每张卡片是一份蓝图：名字、状态（草稿 / 已批准 / 已铸造）、版本号。右列是工作台，从上到下依次是：**动作栏**（保存、校验、批准、铸造上架）、**编辑轨**（表单 / JSON / 起草 三个页签）、**校验结果**、**编辑差异**、**试跑报告**。图里顶部那颗绿色按钮写着「再铸上架（刷新绿色报告）」——它只在蓝图拿到**已签署的绿色报告**后才会亮起，这是本课的终点站，先认个脸。

## 步骤

### 1. 新建一份蓝图

点左列「新建」。系统给一份六段齐全的骨架（场景名占位「未命名场景」），所有字段都可以改。不想从空白开始，就点「起草」页签：把提示词复制给会话里的蓝图构造师，它产出的 JSON 落回同一个草稿池、走同一条校验链——起草不会绕过任何闸门。

### 2. 表单轨：把边界写清楚

![表单轨：场景名、一句话用途、不做什么、数据来源、评审模型，五处都在说「这个团队是什么、不是什么」](https://cms.finddatatech.cloud/uploads/blueprint_studio_02_form_judge_b545ef7787.png)

表单轨管的是蓝图的门面四件事：

- **场景名 / 一句话用途**：这支团队为谁做什么。
- **不做什么**：明确划出界外（比如投研晨会场景写明「荐股、下单」不做）。这一段和用途同样重要——它是日后回答「为什么没做 X」的依据。
- **数据来源**：只填**在册的工具名或逻辑数据源名**（如 websearch）。禁止填接口地址、禁止出现任何凭据——构造间在校验时逐字段拦。
- **评审模型**：给「模型判据」选一位评委。默认「跟随部署默认」，界面会把**实际解析到的模型**回显出来（图例中回显为一枚便宜档模型）；你也可以指定名册里的其他模型。有一条硬规矩：**评委不能是干活的那个模型**——自己给自己打分不作数。

### 3. JSON 轨：岗位、节奏与验收断言

![JSON 轨：同一份草稿的结构视图——岗位编制、编排、节奏、验收断言、看板骨架都在这里](https://cms.finddatatech.cloud/uploads/blueprint_studio_04_json_track_18d30b6a7f.png)

岗位编制（几个岗、怎么接力、多久跑一次）、**验收断言**、看板骨架在 JSON 轨编辑。表单与 JSON 是同一份草稿的两个视图，改哪边都同步。验收断言是整条生产线的核心：它声明「这支团队跑起来以后，怎样才算成立」。两类断言：

- **机器判据**：能直接验的事实，比如「岗位全部落位」「首轮真的点火了」「上报数据真的落地」。跑没跑过，一查便知。
- **模型判据（llm-judged）**：验不了「好不好」的，交给评审模型。每条带一段**判据原文**，如「扫描岗与纪要岗两个岗位在试跑团队中均已落位」，评委读完真实证据后给出三态之一：`pass`（判据满足）/ `fail`（判据不满足）/ `insufficient-evidence`（证据不足以判断）。

只有 `pass` 计入绿色。写判据的经验：**判据要落在证据能承载的事实上**（提到「哪些岗位」「什么产物」，证据里就得有这些身份），空泛的「做得好不好」模型只能回你证据不足。

### 4. 校验：让闸门替你找错

![校验结果：全部通过；有问题时逐字段指名（哪个段、哪一条、为什么）](https://cms.finddatatech.cloud/uploads/blueprint_studio_03_validate_pass_da9765fdd6.png)

动作栏点「校验」。校验链逐段过：形状、数据来源口径、cron 写法、断言闭集、评审模型在册性——**哪一段不合格就点名哪一段**。全绿之后「批准」按钮才会解锁；改过任何一个字段，之前的绿色作废，需重跑校验。

### 5. 批准，然后铸造上架

批准是你作为蓝图主人的签字画押：只有创建者能批。批准后点「铸造上架」——走的是平台既有的发布通道，产出一枚智能体市场里的团队包，带上「谁批的、哪个版本、跑没跑过」的追溯信息。**到这一步团队已经可以安装**，但报告栏还是空的——上架不等于跑通。

### 6. 试跑：真建一支临时团队，真点第一轮

![试跑报告：全绿徽章、逐条断言的判决、模型判绿的理由（引用证据原文）、评审来源与签字行](https://cms.finddatatech.cloud/uploads/blueprint_studio_05_trial_report_8fb75cf02c.png)

报告栏点「试跑」（铸过的蓝图才有这颗按钮）。平台会在隔离沙盒里**真的把岗位建出来、真的点燃首轮**，然后逐条对断言：机器判据直接查事实，模型判据由评委读证据给三态。报告上每个徽章都来自真实执行——绿色不是配色，是账本。

### 7. 签字：双钥匙的第二把

试跑全绿后，报告下方出现「对报告签字」。这一步的意义：**模型判绿只是证据，主人签字才是终审**。两把钥匙都在场，这份报告才支撑可售状态；只签字而模型没判绿，同样不算。

### 8. 再铸上架：把绿色报告刷进包里

拿到「已签署的绿色报告」后，顶部那颗绿色按钮变成「再铸上架（刷新绿色报告）」——再点一次，包里的报告位随之刷新。**收费的团队包以这份绿报告为可售闸**：没跑通的收费包会被拒绝上架。报告被重跑覆盖后，旧签字自动作废、按钮熄灭——想刷新包里的报告，得重新签字。

## 模型判据在看什么

三态之外，构造间把「判据本身跑失败」也单独说清：

- **模型：判绿 / 判红 / 证据不足**——评委真的读过证据了，理由会引用证据原文。
- **模型：未跑成（车道不可用）**——评委根本没联系上（超时、限流、上游故障）。这不是「没通过」，是「没判成」，处置方向完全相反：前者要改证据或判据，后者**重跑即可**。界面对话条、审计件与报告徽章都会写明这一点。

![诚实分层：模型判据条显示「未跑成（车道不可用）」——基础设施故障不会被伪装成判定结果](https://cms.finddatatech.cloud/uploads/blueprint_studio_06_lane_unavailable_e377f0d25f.png)

审计件（判决记录）随报告存档：判据原文、评审模型、证据摘要、模型原始输出、结论与时间，每条都可复核——你随时能查「当时的绿是谁、根据什么给的」。

## 自检

- 蓝图左列状态徽章到「已铸造」，报告栏出现「全绿」，按钮从「铸造上架」变成「再铸上架（刷新绿色报告）」。
- 校验面板显示「全部通过」时，报告里的机器判据条应全部「通过」——两者互相印证。
- 故意把某条判据改严（要求一个不存在的岗位），重跑试跑应见「证据不足」或判红，且绿色作废——闸门在干活。

## 如果没成功

- **批准按钮是灰的**：先跑校验；改过字段后旧校验结果作废，绿灯重跑。
- **试跑报「车道或沙盒故障」类提示**：报告不落账，直接重跑试跑即可；若持续，把时间告诉平台管理员查模型车道。
- **提示所选评审模型不在册**：改选「跟随部署默认」或名册里的模型；部署默认名单由平台管理员配置。
- **铸造被 409 拒绝**：同名包已存在，走「发布新版本」而不是再建一个。
- **报告重跑后签字没了**：设计如此——签字只对当时那份报告生效。
